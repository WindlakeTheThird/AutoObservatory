# Astronomy Math Reference

Techniques used in the [[Autoobservatory Project]] position math.

## Keplerian propagation from mean elements

Element = value_J2000 + rate × (jd − 2451545.0). Solve Kepler's equation by Newton iteration, rotate perihelion→ecliptic→equatorial, convert to RA/Dec. Consistency rule: mean motion must satisfy n = 0.9856076686 / a^1.5 (deg/day) — Saturn's CSV violated this and drifted 0.71° per 26.7 years.

Used for the minor bodies (Pluto, Ceres, asteroids, TNOs) only; the eight major planets are on [[#VSOP87 truncated series|the VSOP87 path]].

## Light-time correction

Iterate ~3×: evaluate the planet at jd − dist/173.15 days (1 AU = 173.15 light-days) and use the retarded geocentric vector. Converges to <1″.

## IAU 2006 precession

ζ, z, θ polynomial angles (Capitaine et al.) built into R3(−z)·R2(**−θ**)·R3(−ζ). ~0.1″ accurate for centuries around J2000.

**The R2 step is R2(−θ), not R2(+θ).** The IAU 2006 matrix mixes x and z with **minus** `sin(theta)`:

```
x' = x·cosθ − z·sinθ
z' = x·sinθ + z·cosθ
```

Implementing the `+sin` form silently yields the **transpose** of the precession matrix, a 2θ ≈ 1071″ (0.3°) rotation error. This was live in both `planetary_objects.h` and `astrop.pas` until 2026-10-08, where it cost the Keplerian bodies 12–18′ of accuracy. It is verified element-by-element against `erfa.pmat06`; see [[Ephemeris Accuracy Verification#2026-10-08 precession sign fix (was silently costing 12–18 arcmin)]].

## Two frames reach the horizontal transform — do not mix them

This is the most expensive mistake in the codebase, and both directions of it have been made:

| Source | Frame | Action |
|---|---|---|
| `celestial_objects.csv` (stars, clusters, nebulae) | **J2000** | **must** be precessed first |
| `GetPlanetaryObjects` — VSOP87 planets | mean equinox **of date** | **never** precess |
| `GetPlanetaryObjects` — Schlyter Moon | mean equinox **of date** | **never** precess |

Catalog rows went un-precessed for a long time and landed **9–21′ off** — more than the firmware's 0.15° deadband. Use `PrecessRaDecJ2000ToDate` (`planetary_objects.h` / `astrop.pas`) for catalog objects. Precessing something already of-date is the same 2θ-class mistake in reverse: the Schlyter Moon lost ~20′ to exactly that early on.

Guarded by `make check-horiz` (`tools/horzcheck.cpp`, `pas/horzcheck_pas.lpr`), which includes a **negative control** — the same objects with precession skipped must fail — so this cannot regress unnoticed.

## VSOP87 truncated series

The eight major planets are evaluated from truncated VSOP87 series generated by `tools/vsop87_gen.py` from the PyMeeus tables (LGPL; attribution is in both generated files). Amplitude units are 1e-8 rad (L/B) and 1e-8 AU (R); terms below ~0.2″ were dropped at generation.

The series are **already referred to the mean equinox of date**, so this path applies **no precession** — doing so was a 0.45° double-precession bug caught by the 2026-10 audit. The pipeline is: heliocentric ecliptic L/B/R → FK5 correction → geocentric vector with 3-iteration light time → annual aberration → rotation by the mean obliquity of date.

The two generated tables (`vsop87_trunc.h`, `pas/vsop87_trunc.inc`) are cross-checked by `make check-vsop` (`tools/vsopcheck.py`): term count, all 40,137 amplitudes, all 13,379 t-power bytes, all eight series layouts and the planet names. `make check` cannot do this — ephcheck's tolerance is 108″ while one term is worth ~0.2″.

## Annual aberration

Add k·v_earth (k = 0.0057755 d/AU = 1/c) to the geocentric vector, with Earth's velocity from a **central difference over 0.01 day** on the VSOP87 path.

An earlier version differenced over **±0.5 days**, which applied only about half the ~20.5″ effect; that was found and fixed in the 2026-10 VSOP87 upgrade. If you are reasoning about aberration and the numbers look like half of what you expect, check the differencing interval first. Signature it is correct: the transverse component nearly vanishes for outer planets near opposition.

## H-G phase function (minor bodies)

Asteroids and distant small bodies (CSV rows with phase slope `G > 0`) use the IAU H-G model:

`mag = H + 5·log10(r·d) − 2.5·log10(Φ(α))`, with `Φ(α) = (1−G)·Φ1 + G·Φ2`,
`Φ1 = exp(−3.33·tan(α/2)^0.63)`, `Φ2 = exp(−1.87·tan(α/2)^1.22)`,
and α the Sun-object-observer phase angle. The distance-only form `H + 5·log10(r·d)` is only correct at opposition, so without this an asteroid fades/over-brightens by up to several magnitudes as its phase angle grows. Verified against JPL Horizons apparent V magnitudes (11 objects, ≤0.01 mag). `H` and `G` come from Horizons — true absolute magnitudes, since every minor-body orbit except Pluto's uses Horizons osculating elements at (or back-propagated to) J2000. Mercury/Venus use a Lambert phase term `−2.5·log10((1+cos α)/2)` instead. The Schlyter phase model for the planets diverges from Horizons APmag at large phase angles (Mercury ~1.7 mag worst near inferior conjunction); positions are unaffected.

**Two traps here.** The tangent is taken on the **radian** half-angle — tan(60°) ≈ 1.73, not tan(60 rad); the first hand-computed reference table used degrees and was wrong by up to 0.28 Φ. And the Pascal mirror once selected the Mercury/Venus correction by matching semi-major axis (`a = 0.387098/0.723330`), so a data refresh silently disabled it; it now selects by object name.

**Regression guard:** `HGPhase()` lives in one place per language (`planetary_objects.h` / `astrop.pas`) and is pinned by a frozen-value unit test (`tools/hgcheck.cpp` + `pas/hgcheck_pas.lpr`, run by `make check-hg`). 19 (G, α, Φ) cases — including the G ≤ 0 short-circuit and α up to 120° — must produce identical output in both languages.

## Limited views (azimuthal equidistant projection)

The full-sky map is an azimuthal equidistant projection about the zenith: the angular distance from the centre (90° − altitude) maps linearly to the drawing radius. A limited (`--fov`) view generalises the same projection to an arbitrary centre (az₀, alt₀):

- tangent-plane components at the centre: `x = cos h·sin(ΔA)`, `y = −sin h₀·cos h·cos(ΔA) + sin h·cos h₀` (with ΔA = az − az₀)
- angular distance θ from `cos θ = sin h₀·sin h + cos h₀·cos h·cos ΔA`
- `u = (θ / (fov/2)) · x/sin θ` (screen right), `v = (θ / (fov/2)) · (−y/sin θ)` (screen **up**, then y is negated when drawing because screen y grows downward)

Points with θ > fov/2 are outside the field and are not drawn. At the default centre (az₀ = 0, alt₀ = 90, fov = 180) this reduces **exactly** to the original `u = (1 − alt/90)·sin(az)`, `v = (1 − alt/90)·cos(az)`, which `tools/viewcheck.cpp` and `pas/viewcheck_pas.lpr` pin on a grid of az/alt (so the full-sky map cannot drift). The `−y`/`−sin θ` keeps the planisphere mirror — increasing altitude is toward the drawing centre — so a zoom is a magnified patch of the existing map, N up / E right. The fov is a **diameter**, so `fov = 180` is the whole visible hemisphere and valid inputs must satisfy `0 < fov < 180`. A hair of tolerance (`+1e-12` rad) keeps points exactly on the field edge (the horizon at fov 180), where `cos()` rounding lands θ a few ULP either side of fov/2 depending on azimuth.

**Follow mode** adds no new math: it simply drives the centre (az₀, alt₀) each frame from the locked target's current horizontal coordinates, so the same projection tracks the object as the sky turns.

## Schlyter lunar model

Elements measured from 1999-12-31 0h UT (JD 2451543.5) — NOT J2000 noon. Perturbation terms (evection −1.274°, variation +0.658°, yearly equation −0.186°, +9 more longitude, 5 latitude, 2 distance) must derive D = Lm − Ls and F = Lm − N from the SAME element set; mixing in Meeus mean-element constants inverts improvements.

Output is already equinox-of-date, so **no precession** is applied (see [[#Two frames reach the horizontal transform — do not mix them]]).

## Sidereal time

GMST comes from the standard IAU polynomial evaluated on the UTC-derived JD. **UT1−UTC is deliberately not corrected.** Measured against astropy at 2026-09-23, the genuine UT1−UTC effect is only **−0.20″**, and the polynomial already sits within +0.06″ of the reference, so an IERS ΔT table was tried and reverted — it made the result worse (−1.24″) while adding a table that goes stale. `Ut1MinusUtcSeconds()` remains in `astro_math.h` as a documented zero-returning stub.

The common mistake is assuming the correction is the leap-second count. It is not: the offset that matters is UT1 − UTC, and because Earth keeps slowing, TAI − UT1 has grown past 37 s and absorbs nearly all 37 leap seconds. "37 leap seconds" overstates the error by roughly 20×.

## Residual budget

| Effect | Size |
|---|---|
| VSOP87 planets, measured vs Horizons (48 epochs) | 0.15–0.40′ avg, ≤2.1′ max |
| Missing nutation | ~17″ |
| Missing aberration 2nd order | <1″ |
| UT1−UTC not applied to GMST | **0.2″** (measured; see above) |
| Moon (Schlyter + main terms) | ~0.8′ |
| Catalog stars, horizontal | 0.002–0.008° residual vs astropy apparent |
| Keplerian minor bodies | element-limited now: Pluto 0.3′, Ceres 0.6′, Eris 2.6′ |

The old "mean-elements model floor ~9–17′" no longer applies — that model was replaced by VSOP87 in 2026-10.
